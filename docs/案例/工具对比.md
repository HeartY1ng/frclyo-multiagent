# 工具对比：保留什么，借鉴什么

**结论：保留自己的执行、契约和验收体系，有限投入只读看板；需要更完整的开发交互时，再做隔离试点。** 这是对当前目标的工程取舍，没有实测性能或维护工时排名。

## 值得借鉴的能力

Vibe Kanban 的工作区与代码审查适合需要持续改代码、看差异、给反馈的流程；codex-orchestrator 的回合状态、阻塞原因和追问机制适合长期 Codex 会话。本项目可借鉴状态拆分和审查方式，先把“谁在执行、谁需要输入、证据齐不齐、是否已验收”表达清楚。[1][2][4]

整体迁移仍需补任务契约、路由规则、权限配置、回执和验收接口；混用还会增加两套状态及停止／重试的协调。原报告另记录 Vibe Kanban 快照 README 的 sunsetting 声明（18–20 行），这里只保留为当时的维护风险依据，不据此断言当前服务状态。

## 本项目也需要补齐的边界

原报告指出，OpenCode 沙箱没有显式禁止网络，回执哈希没有覆盖全部交付物，回执也不能作为防篡改证明。本项目要先验证这些基础能力，再决定是否增加交互界面。[5]

如做混用试点，建议以任务号和轮次关联外部 workspace/job，明确谁负责停止与重试，最终验收仍由独立检查产生。这是建议接口，尚未实现。兼容性、实际网络连接和维护成本需要在隔离环境以小任务实测。
