# 任务分类标准（v1，2026-10-13）

> 用途：大脑（当前是 Claude）接到一件活，**先按本标准写出一段"分类与难度分析"，再决定拆不拆、派给哪个"框架 × 模型"、怎么验收**。
> 依据：路由研究（VDAR-Router、Routesplain、Agent-as-a-Router，2026）指出：先写出明确的难度分析再选模型，比只看题面准；而复杂度判断是整个路由里最难的一环，所以用多个维度、而不是一个笼统的"难不难"。出处见文末。

## 一、七个维度

### 1. 类型（这是什么活）
| 代码 | 类型 | 例子 | 备注 |
|---|---|---|---|
| T-code | 编程改动 | 改引擎、加功能、修 bug | 通常和项目其他部分强耦合 |
| T-review | 审查 | 代码审查、方案挑错 | 审查者要和产出者**不同来源** |
| T-research | 调研 | 查资料、比较方案 | 适合并行（Anthropic：广度类任务适合多 agent） |
| T-gen | 批量生成 | 生成语料、改写一批文案 | 量大，重点看成本和风格多样性 |
| T-convert | 精确转换 | 拼音转汉字、格式转换、翻译 | **要求忠实于输入**，不允许改写（Space Bunny 就是栽在这里） |
| T-analysis | 分析与方案 | 架构设计、取舍分析 | 需要推理，难以机器验收 |
| T-decide | 决策 | 有争议、多选一 | 用群贤 |
| T-data | 确定性数据处理 | 统计、去重、排序、切分 | **应该写脚本跑，不该让模型逐条处理**；模型只负责写脚本 |
| T-media | 多模态 | 看图、识图 | 先查模型支不支持（DeepSeek v4-pro 不支持图片） |

### 2. 耦合度（和别的部分牵连多深）
| 级 | 含义 | 判断方法 |
|---|---|---|
| C0 独立 | 和别的任务没有共享的文件、数据和决定 | 换一个人单独做也不会影响别人 |
| C1 弱依赖 | 只通过**事先约定好的接口**交接（文件格式、函数签名） | 能把接口写成一页纸的契约 |
| C2 强耦合 | 共享代码、共享状态，或者很多细节要临场商量 | 写不出简短的契约，或者改一处会牵动很多处 |

### 3. 可验证性（做完怎么知道对不对）
| 级 | 含义 | 例子 |
|---|---|---|
| V1 机器可验 | 有测试、有标准答案、有格式校验 | 单元测试、考卷、格式检查 |
| V2 抽查加交叉审 | 没有标准答案，但能抽查，也能让另一家模型挑错 | 语料质量、文档 |
| V3 只能由人判断 | 品味、策略、对外沟通 | 文案风格、商业决策 |

### 4. 难度（用客观指标定级，不凭感觉）
| 级 | 指标（满足任意两条就算到这一级） |
|---|---|
| L1 机械 | 1 步或几步；规则明确；没有歧义；照着模板就能做 |
| L2 常规 | 涉及 1～3 个文件或环节；有少量判断；同类活做过 |
| L3 复杂 | 涉及 4 个以上文件或环节；需要取舍；有歧义要先澄清；没有现成套路 |
| L4 前沿 | 需要新的算法或设计；公开资料少；做错的代价大；需要多轮试验 |

### 5. 风险（做错了会怎样）
| 维度 | 低 | 高 |
|---|---|---|
| 能否撤销 | 只写在交付目录里，删掉即可 | 改项目仓库、改全局配置、对外发送 |
| 影响范围 | 只影响这一件活 | 影响 用户 的手机、电脑、账号或别的项目 |
| 数据敏感度 | 公开、模型编的内容 | 用户 的私人信息、未公开的代码、工作资料 → **不能给来路不明的免费模型** |

### 6. 规模与预算
条数、token 量估算、可接受的花费和时间。**花钱的活先按官网现价报预算。**

### 7. 上下文需求
| 级 | 含义 | 对派活的影响 |
|---|---|---|
| X1 自带 | 任务卡里写的东西就够了 | 谁都能接 |
| X2 要读资料 | 需要几份文件（复制进交付目录） | 要看上下文长度 |
| X3 要懂项目全貌 | 需要项目历史、来龙去脉 | **不适合外包**，由大脑自己做或强耦合处理 |

## 二、维度怎么决定做法
| 情况 | 做法 |
|---|---|
| T-data | 不让模型逐条处理：派一个编程工人写脚本，由脚本处理全部数据 |
| C2 强耦合或 X3 | **不拆**，交给一个工人完整做，或者大脑自己做 |
| C0 / C1 且量大 | 可以拆，按《任务拆分与集成规范》先写契约再拆 |
| V3 | 产出要交给 用户 拍板，不能由 agent 自己验收 |
| V2 | 验收方式：抽查 + 另一家模型交叉审 |
| L1 | 选最便宜最快的组合（目前是 OpenCode + DeepSeek flash） |
| L3 / L4 + T-code | 选最强的组合（目前是 Codex + GPT 高档位；额度紧时用 OpenCode + DeepSeek v4-pro），并加交叉审查 |
| 风险高 | 改动只落在交付目录，由大脑核对后再并入；对外的操作一律先问 用户 |
| 数据敏感 | 只用 用户 自己配置的 API，不用免费模型 |

具体模型的选择看路由表（[`大脑手册.md`](../../大脑手册.md) 第四节）。这张表要不断用**表现记录**按维度统计的结果来修正（依据 Agent-as-a-Router：按任务维度统计各模型表现，路由效果提升 15.3%）。

## 三、写给大脑的"分类与难度分析"格式（派活前必须写）
```
类型：T-xxx
耦合度：Cx（理由：……）
可验证性：Vx（怎么验：……）
难度：Lx（满足的指标：……）
风险：能否撤销 / 影响范围 / 敏感度
规模与预算：……
上下文需求：Xx
结论：拆不拆、派给谁（框架 × 模型 × 档位）、怎么验收、能并发几个
```
这段分析写进任务卡开头，同时把维度记进表现记录。

## 出处
- VDAR-Router（arXiv 2607.18098）：先写出难度分析，再结合历史上难度相近的例子选模型
- Routesplain（arXiv 2511.09373）：按任务类型、领域、复杂度等可解释的概念来路由；复杂度判断是瓶颈
- Agent-as-a-Router（arXiv 2606.22902）：加入按任务维度统计的表现数据，相对提升 15.3%
- Anthropic《Building Effective Agents》、多 agent 研究系统：广度类任务适合并行，强耦合的编程不适合
- 本项目实测：`projects/zh2en-语料/难题测试/`、`试生成/`
