# 为什么这样设计

frclyo-multiagent 想把本地已经准备好的 agent 和模型 API 变成按任务取用的资源池。能否完成一件活，取决于任务是否清楚、工具是否可用、结果是否能验，不只取决于同时启动了多少个 agent。

本文区分设计目标和历史经验。安装器、钥匙串接入、完整网络隔离与按账卸载仍须实现或验证；不能把这些要求当成已有安全保证。

## 大脑和工人分开

大脑保留目标、上下文和裁决权：先判断要做什么、能否拆、怎么验，再选择工人。可以把已有订阅额度用于 Claude 或 Codex 大脑，把边界清楚的任务交给成本较低的模型 API 工人。这里是一般资源分工，不依赖特定套餐，也不保证所有任务都会更便宜。

“便宜”要连同返工和验收成本看。确定性统计交给模型写出的脚本执行；涉及取舍的任务由大脑保留判断；强耦合的修改通常交给一个工人做完整。资源池需要通过小任务校准“框架 × 模型 × 档位”，然后按实际表现更新选择。大脑更换时，接手者从契约和台账恢复，而非依赖上一段聊天的记忆。

## 契约先行，把隐含决定提前写出来

Cognition 的 Flappy Bird 例子中，背景和鸟分别交给不同 agent，可能得到风格和行为不相容的两份产物。动作本身携带决定；没有共享的前提，会在集成时变成冲突。[出处：Don’t Build Multi-Agents](https://cognition.ai/blog/dont-build-multi-agents)

本项目的做法是先写共享决策记录，再按可独立验收的产物拆分。契约必须落到编码、分隔符、排序、空值、坏输入、文件归属和样例。每个工人拿到全文；同一个文件只有一个写入者。写不清接口，或拆分后仍需要频繁临场商量，就不拆。契约不能消除所有歧义，所以交付时还要披露自行决定的细节，遇到影响别人的未定事项则报告“需要输入”。

## 证据验收，让“完成”有可检查的含义

MAST 总结了 14 种失败模式，涉及系统设计、agent 间协调和任务验证。对本项目直接有启发的包括缺少澄清、推理与行动不一致、过早结束及验证不足。[出处：Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)

我们的对应机制是：执行器记录退出事实和回执，工人交出实际文件与决策披露，集成者复跑验收。三关分别检查格式与接口、各方决定是否一致、完整流程是否正确。能构造参考实现的确定性任务，优先做字节对比；文风等主观判断仍由使用者决定。

回执也有边界。历史实现的哈希只覆盖结果说明，没有覆盖所有交付文件；回执与产物处于可写目录，不能因此宣称防篡改。退出码为零、看板显示结束、说明里写“测试通过”，都不能单独证明交付正确。这个缺口来自原对比报告的静态审阅，见[工具对比](案例/工具对比.md)。

## 默认安全必须用实际行为验证

设计要求是工人只在本轮目录写入，敏感目录不可读，密钥不进入任务对话或项目文件。计划由 macOS 钥匙串保管密钥；工人直接网络访问默认受限，模型调用仅经受控的本机白名单代理放行。网页搜索属于单独能力，只在任务需要时开放，例如获取官方许可证原文。

这几个边界要分别验证：文件沙箱不能自动证明网络被阻断；关闭网页搜索也不等于禁止 shell 联网；允许调用模型 API 不能扩大成任意外联。发布前应使用假密钥、哨兵文件和无敏感内容的任务，实际检查越界读取、越界写入、子进程和网络访问。历史 OpenCode 工人的网络限制存在缺口，尚不能把目标写成现状。

## 一切可撤销，要先记清改过什么

任务台账保存事实、未知项和计划，进度台账保存每轮进展与下一步；连续无进展时重新规划。这借鉴了 Magentic-One 的任务与进度台账机制。[出处：Magentic-One，第 4.1 节](https://arxiv.org/html/2411.04468v1)

在此基础上，本项目要求每轮交付独立存放，未验收不自动并入；安装变更也要登记，计划由 `aw uninstall` 按台账撤销安装动作。撤销能力须限定范围：外部请求已经产生的费用、已经发送的数据，不会因为删掉本地目录而消失。卸载脚本也必须识别项目安装项，不能把使用者原有工具或交付成果当作安装残留删除。安装与卸载流程仍需在干净环境实测。

## 踩过的坑，留下可复用的教训

以下经历按本次文档任务提供的历史摘要整理；不公开个人运行记录，也不补写未提供的事故细节。它们不是对相关工具所有版本的结论。

| 经历 | 学到了什么，以及本项目的应对 |
|---|---|
| 早期用来调度的 agent 三次自述失实 | 不能由执行者一句“已完成”决定状态。完成、收到与验收必须有对应证据。 |
| 任务编号撞号 | 编号需要统一分配与唯一性检查，重试使用新的轮次，账本不能让不同任务互相覆盖。 |
| “文稿”文件夹遇到权限问题 | 目录存在不代表工人可访问。工作区位置与权限应在安装和自检阶段确认；计划统一使用专门的工作根目录，避免把额外授权当成默认前提。 |
| 工人沙箱没有真正断网 | 写入范围受限和网络受限是两件事。必须用实际连接测试确认策略，再区分模型 API 通道、网页搜索与其他外联。 |
| 某些模型在命令行版用不了 | 网页可见或配置中列出，不等于当前 CLI、认证方式和推理档位可调用。升级后用小任务检查实际返回与能力；计划由 `aw doctor` 和 `aw calibrate` 支持。 |

这些教训最终落在同一处：把不可见的假设写成契约，把完成状态绑定到产物，把一次失败变成下一轮能检查的规则。[切词实战](案例/2026-10-13-切词实战.md)展示了这个过程，也保留了通过本次验收后仍需改进的边界。
